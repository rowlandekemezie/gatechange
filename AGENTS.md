## Deploy

- CI (`.github/workflows/ci.yml`) runs `pnpm turbo run check test build --concurrency=1` on every pull request and push that changes more than Markdown, `docs/`, or `LICENSE`. A new push to a pull request cancels its running CI, and runs share Turbo's cache through the Actions cache. A push to `main` that passes deploys the `prod` stage and smoke-tests `https://jobs.rowlandekemezie.com`.
- CI authenticates with the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets. `apps/infra/stacks/github.ts` mints that scoped token and writes both secrets; run it with `pnpm infra:ci-credentials --profile admin` to create or rotate them.
- Local deploys use an Alchemy profile: `pnpm alchemy profile edit --add Cloudflare`, then `ALCHEMY_PROFILE=<name> pnpm infra:plan --stage prod` and `pnpm infra:deploy --stage prod`.
- The zone `rowlandekemezie.com` must already be on the Cloudflare account. Alchemy attaches `jobs.rowlandekemezie.com` as a Worker custom domain.
- Mail sends from `sign-in@jobs.rowlandekemezie.com` and `digest@jobs.rowlandekemezie.com` (`MAGIC_LINK_SENDER` and `DIGEST_SENDER` in `apps/api/src/worker.ts`). Email Sending is onboarded on the `jobs.rowlandekemezie.com` subdomain, not the root domain; a root-domain sender fails with `E_SENDER_DOMAIN_NOT_AVAILABLE`.
- `DIGEST_SENDS_PER_RUN` and `DIGEST_DAILY_SEND_LIMIT` (apps/api/.env.schema) bound saved-search digests. Email Sending gives new accounts a small daily quota that sign-in links share, so keep the daily limit under it. Instant alerts get 20 percent of the daily limit and weekly digests the rest, so instant alerts never shrink weekly delivery. A Pro member gets at most `INSTANT_SENDS_PER_MEMBER_PER_DAY` (6) instant emails in any 24 hours.
- Pro plans come from `PRO_PLANS` (JSON, described in `apps/api/.env.schema`), never from code. Each entry is an Alchemy `Stripe.Price` named `Pro<plan>Price`. Never drop or reprice a plan that has subscribers; set its `onSale` to `false` so the webhook still grants Pro. Empty `PRO_PLANS` hides billing.
- Billing is off unless `BILLING_ENABLED=true`. With it on, the Alchemy profile needs a Stripe key, and the deploy refuses a key in the wrong mode: prod needs live keys, every other stage needs test keys. Prod also needs `STRIPE_RESTRICTED_KEY`, an `rk_live_` key made in the Stripe Dashboard with Checkout Sessions, Customers and Customer portal write only. Alchemy `2.0.0-beta.83` cannot mint restricted keys, and without that value its token falls back to the profile's account secret. The prod webhook ignores events with `livemode: false`, and every other stage ignores `livemode: true`.
- Stripe Managed Payments is turned off per Checkout session (`managed_payments.enabled=false`), so the operator stays merchant of record with no automatic tax. Managed Payments refuses a Price whose Product has no tax code, and Alchemy's `Stripe.Product` has no `tax_code` prop. Turning it on needs a tax code set outside Alchemy.
- Migration `0008_billing.sql` cannot be removed once a stage has applied it. Deploying code without it fails with `RewrittenMigrationHistoryError`, so roll back billing with a forward revert that keeps `0008_billing.sql`.
- `INGEST_FEEDS_PER_RUN` and `INGEST_FEED_CONCURRENCY` (apps/api/.env.schema) tune the cron. Workers Free allows 50 external subrequests (`fetch`, retries included) and 1,000 to Cloudflare services such as D1 per invocation, and 10 ms CPU; waiting on I/O is not CPU. A board feed costs one fetch. Each fetch can retry twice on a transient error, and every redirect hop counts as a subrequest.
- After each ingest run the cron queues up to `ENRICHMENT_SWEEP_LIMIT` company-board listings first seen in the last `ENRICHMENT_SWEEP_HOURS` (default 24) that have no model enrichment from the current `MODEL_ANSWER_VERSION` and no final skip. A model enrichment from an older prompt version is queued again after every listing with none, so a prompt change backfills the window once; the enrichment records the version it ran with even when the new fields come back null, so it is not queued again. A null in the newer answer keeps the value the older prompt saved. The limit defaults to 8 on the `prod` stage and to 0 on every other stage, so a verify stage left running makes no model calls; set it explicitly to enrich on a verify stage. Each run's log line names the limit and the stage. After a prod deploy, check the cron log for `limit=8 stage=prod`; `limit=0` means the stage binding did not resolve and prod enriches nothing.
- Alchemy keeps the old binding when an env var is unset. Removing `ENRICHMENT_DAILY_NEURONS` or `ENRICHMENT_SWEEP_LIMIT` from the deploy environment and redeploying plans `no changes`, and the stage keeps the old value, not the default. To change either one, set it explicitly to the new value, even when that value is the default.
- `ENRICHMENT_DAILY_NEURONS` (default 29,000) is the hard spend cap, counted in neurons, Workers AI's billing unit. Before fetching a posting the consumer reads the UTC day's claimed neurons from the D1 table `enrichment_neurons` and skips as `DailyCapReached` when the costliest possible call (519 neurons, with up to 448 answer tokens) would not fit. After the fetch it claims the call's worst-case cost in one atomic statement and calls the model only when the claim fits. The worst case counts every prompt byte as a token, because a Llama 3 token is at least one byte, and the prompt is cut to 16,000 bytes, so no call can cost more than it claimed. Queue redeliveries claim again. After the call, one atomic `UPDATE` adds the neurons Workers AI reports to the day's `used` column and moves `claimed` from that call's claim to the reported neurons. It drops by the unspent part when the report is under the claim and rises by the overage when the report is over it, so the gate counts real spend; it never goes below 0. The consumer trusts a report only when both token counts are non-negative integers and `prompt_tokens` reaches the conservative lower bound from the fixed system prompt's letter runs (currently 408, implying at least 11 neurons for the pinned Llama model). A Llama 3 pre-token holds at most one letter run. Schema and chat-template tokens are excluded from this lower bound because their contribution to reported usage is not guaranteed; the separate worst-case claim still includes both. A call with no report or an untrusted one keeps its full claim and adds nothing to `used`, and the `UPDATE` itself ignores a negative report, so `used` never decreases. So `claimed` is the neurons that reconciled calls spent plus the full claims of calls still in flight or with untrusted usage.
- Cost. llama-3.3-70b-instruct-fp8-fast costs 26,668 neurons per million input tokens and 204,805 per million output tokens, at $0.011 per 1,000 neurons after 10,000 free a day (Cloudflare pricing page, updated Oct 15 2026). At the default budget the worst case is 29,000 neurons a day. With no free neurons left (another workload on the account spends them) that is 29,000 x 31 x $0.011 / 1,000 = $9.89 for a 31-day month, so one enriching stage stays under $10 in every month. With the free 10,000 unused elsewhere it is (29,000 - 10,000) x 31 x $0.011 / 1,000 = $6.48. Each other stage that enriches adds up to $9.89. A 4,000-character posting claims 292 neurons and a 12,000-character one 506. Because the ledger is reconciled to reported usage, the budget covers about (29,000 - 519) / 62.6 = 454 calls a day at the measured average of 62.6 neurons a call; if Workers AI never reported usage it would cover 55 calls at the 519-neuron ceiling.
- The sweep takes the newest listings first. A board that publishes more than the budget covers in a day keeps the window full of new ids, so older listings from quieter boards can wait until they age out of the 24-hour window. A listing the sweep queues while the budget is spent keeps a `DailyCapReached` skip row until it is enriched; saving an enrichment deletes the listing's skip row. A listing the sweep never reaches before it ages out has no row at all. This costs coverage, not money.
- A listing skipped as `ModelUnavailable`, `PostingUnavailable` or `DailyCapReached` keeps its skip row and is swept again after fresh listings; `Gone`, `Malformed` and `EmptyPosting` are final. A defect in the answer guards records a final `Malformed` skip instead of failing the queue batch. A missing or invalid `handsOn` or `handsOnQuote` decodes as null and does not make the answer `Malformed`.
- The answer guards are tuned on the golden, held-out, field and regression sets in the J6 receipts, so their scores on those sets are not an unbiased estimate. Fresh rows drawn after the code is frozen are the only fair measure.
- Verify procedure for a golden eval worker, a throwaway Worker that sends postings straight to the model. Deploy it only to a `verify-*` stage, never with a custom domain. It must reject any request without a shared-secret header (generate the secret per run, pass it as a Worker secret, never log it). It must claim each call's neurons from a D1 budget through the same `claimNeurons` statement prod uses, with a small daily budget, and refuse when the claim fails. The harness that deploys it must destroy the stage in a `trap … EXIT` so a crash, timeout or Ctrl-C cannot leave it running, and must confirm the destroy with a Workers list. An orphaned round-10 golden worker stayed public, unauthenticated and uncapped for hours because none of these held.

## Project law

- One contract, every surface. `listJobs`, `boardStats` and `getJob` live in `packages/core/src/contracts.ts`; the browser and the Worker share them through `toRpcGroup` and `toRpc`.
- Core owns ports and domain rules. HTTP lives in `packages/job-sources`, SQL in `packages/job-store`.
- The store is the system of record for listings. Each feed owns its rows: a successful fetch upserts what it listed and departs rows it did not list (`jobs.departed_at`), under the rule for its `FeedRef.coverage`. `feedRefOf` sets coverage from the source's `kind`. A `Complete` feed (a company board) lists everything open, so absence is departure. A `Window` feed (an aggregator) returns a sliding window, so absence means nothing until `WINDOW_HOLD_MILLIS` (30 days) after the posting date. That is Jobicy's own `validThrough` (posting date plus 30 days, sampled from its pages) and inside Himalayas' 60-day `expiryDate`, so `posted_at` carries it and no column stores it. A job page's `validThrough` follows the same rule: `coverageRules` gives a company board's row `last_seen_at` plus 30 days and a `Window` row the later of `posted_at` plus 30 days and `last_seen_at` plus one day, so the markup never outlasts the hold by more than a day and a role its feed still lists never reads as expired. A listed row stays however old its posting. A `Complete` feed admits a role however old its posting, once, with a first sighting (`LongOpenListing`); a `Window` feed admits a new row only when it was posted within `ADMISSION_DAYS` (30). A row a feed lists past that age takes `markListed` on later fetches, with no upsert or sighting, so it costs one row write a fetch. A failed fetch changes nothing and backs the feed off.
- Every admitted run prunes rows departed more than a day ago and rows whose feed has not listed them for 30 days, the cap for a feed that stopped being fetched. A feed removed from the catalog is never fetched again, leaves `feedHealth` at once because that query reads catalog keys only, and keeps its `feeds` row; its listings stay open until that cap prunes them, so keep the source in `SourceName` until no row needs decoding. SmartRecruiters left the catalog because its `robots.txt` allows `/v1/companies/` for LinkedInBot only; the name stays for its rows and `job_enrichment.board`. Each admitted run that completes its database writes records a receipt in `ingest_runs`; rejected lease claims write nothing. The prune preserves `job_history`.
- Ingest runs never overlap. A run first claims the one-row `ingest_lease` for 15 minutes, the Cron Trigger wall-time limit, and releases it when done; a run that finds it held fails with `IngestInProgress` and writes nothing. `job_history.sightings` counts runs in start order, so it is only correct under this lease.
- `job_history` keeps one row per role fingerprint and survives the prune, so days open and repost counts outlive the `jobs` row.
- `intel_history` keeps a record per company slug and role fingerprint from sources whose terms allow paid features, plus the role's company, its current stint and its previous stint. `jobs.company_slug` is derived with `companySlugOf` in the same upsert and indexed for exact company reads. Pro company intel reads it and never `job_history`, so a Remotive or Hacker News sighting cannot move a Pro number. Days open count the current stint; a role that arrived long open counts from its posting date instead, so a backfilled role is not one day old. Reposts count every reopening, but a different feed picking up a posting older than the last sighting is the same posting and neither reopens the stint nor counts as a repost. `MIN(first_seen_at)` over its index is when tracking began.
- Parse every external payload with Effect Schema at the boundary. One malformed listing is skipped, never the whole feed.
- Respect sources: identify the crawler with `USER_AGENT`, keep the per-source minimum intervals in `feed-spec.ts`, link every listing to its original posting, and credit aggregators in the footer.
- No comments in code (`no-comments/no-comments`). Directives with a reason and `SAFETY:` lines survive.
- Prefer property and model tests. `packages/core/test/ingest.model.test.ts` is the model for feed replacement.

## Architecture

```text
cron (20 min) ─▶ JobsBackend.runIngest ─▶ PostingFeeds ─▶ public job APIs
                         │
                         ▼
                      JobStore ─▶ D1 (jobs, feeds, ingest_runs, job_history)
                         ▲
browser ─▶ Website /rpc ─┤─▶ JobsBackend listJobs / boardStats / getJob
agent ─▶ Website /mcp ───┘   (rate-limited at the edge, token-checked in JobsBackend)
```

- `selectDueFeeds` picks the feeds that are due, oldest attempt first, with exponential backoff after failures.
- `listJobs` deduplicates the same company and title across sources and prefers the company board.
- `listJobs` reports each listing's `status`, derived by `listingStatus` in `packages/core/src/listing-status.ts`: `departed`, else `new` (first seen within a day, unless `arrivedLongOpen`: posted over 30 days before the board first saw it), else `boarding` (posted within 7 days), else `on_time`. Every reader that treats a row as open skips departed rows during their last day: `listJobs`, `getJob` (`JobStore.find`), company pages and intel, board stats, saved-search digests and instant alerts, the tracker's `listed` flag, and the enrichment sweep. Only the enrichment consumer opts in through `JobStore.findIncludingDeparted`. A surface that shows departures must opt in the same way, never by widening a default. There is no `final_call`: a row departs on the first successful fetch that its feed's coverage rule lets drop it, so nothing sits between listed and departed.
- Relevance is `role weight + region weight + salary and remote bonuses - 2.5 per day of age`, so a long-open role ranks below fresher ones without a separate rule.
- The edge Worker caches `boardStats` in the `pages` edge cache for 10 minutes, keyed by the shell like a page, and stamps `generatedAt` at render. A page render reads the cached stats, so a burst of board pages costs one query per data center, plus any requests racing the first write. The browser fetches stats only on the board and only when the preload has none. Stats on a page can lag by up to 20 minutes on a cached home page, 10 in this cache and 10 in the page cache. `/rpc` itself is not cached.
- `boardStats` reads `jobs` once. `boardCountsStatement` returns one row per role, region and company with listed and deduplicated counts, and `boardCountsOf` folds them. `/sitemap.xml` calls `sitemapJobs` once, which reads only the columns the sitemap needs, capped at `SITEMAP_JOBS` (3,000). Offset pages re-ran the full window query per page, so their cost grew with pages times rows.
- `MAX_AGE_DAYS` (3650) is the widest `maxAgeDays` a query may ask for and the window company pages, role hubs, the sitemap and `boardStats` read. `ADMISSION_DAYS` (30) is the admission and retention window; do not use one for the other. A long-open role is never `new`, never counts in `newToday`, and never reaches a digest or instant alert, because those promise new roles.
- A signed-out viewer's shortlist (Saved, Applied) lives in `localStorage` only. A signed-in member's shortlist is a tracker in `tracked_jobs` (Saved, Applied, Interviewing, Offer, Rejected, with notes and dates). After sign-in, a non-empty `localStorage` list is offered, not imported; only the Move button imports it, skips jobs already tracked, and clears it. Never re-add a silent import: it would reopen the J7 login-CSRF backstop. Every tracker capability takes its owner from the session, never from input.
- `JobsBackend` serves better-auth under `/api/auth/*` and resolves each `/rpc` request's session into a `CurrentViewer` (`Anonymous` or `Member`) before the RPC server is built. A request with no session cookie skips the lookup. Member-only capabilities fail with `Unauthorized`.
- better-auth runs with runtime schema validation off (`validateSchema: false` in `packages/accounts/src/options.ts`). If the auth tables drift from the migrations, session lookups fail and the viewer reads as signed out, with only a WARN in the logs. The `auth schema` test in `packages/accounts/test/auth-flow.test.ts` fails on that drift, so add a migration with every better-auth upgrade or option change that adds a column.
- A magic link counts against its address only after better-auth has validated it. The budget key is the address better-auth will mail, lowercased, with any `+tag` dropped on every domain, so throwaway tags share their base address's budget. Only `gmail.com` and `googlemail.com` also fold dots, because Gmail delivers every such spelling to one inbox. Each key gets 3 sends and 6 attempts per 15 minutes, and `INBOX_DAILY_SEND_LIMIT` (6) sends a UTC day. Each client gets `CLIENT_DAILY_SEND_LIMIT` (5) sends a UTC day, keyed by `cf-connecting-ip` with IPv6 collapsed to its /64. The whole site gets `MAGIC_LINK_DAILY_SEND_LIMIT` a UTC day, and an address with no verified account may spend only 40 percent of that (`newAddressDailySendLimit`, 360 of 900), so strangers can never use up a verified member's sign-in. The client and inbox limits treat every address alike, so a refusal never says whether an address has an account; only a spent new-address share does. All daily counters are keyed by the UTC date (`magic-link-client:<YYYY-MM-DD>:<ip>`, `magic-link-inbox:<YYYY-MM-DD>:<inbox>`, `magic-link-new:<YYYY-MM-DD>`, `magic-link-global:<YYYY-MM-DD>`), so they reset at midnight and steady traffic never carries a count into the next day. A request with no `cf-connecting-ip` counts in one shared `unknown` client bucket and logs a warning; `x-forwarded-for` is never read. better-auth's limiter deletes these rows once their last count is a day old, because `emailSendLimit` registers a one-day window. A refusal from any daily cap gives back the address's send and attempt and every daily count already claimed. A failed send gives its send and its inbox day count back. It gives its attempt back only when the Email Service error code names a provider fault (`PROVIDER_FAILURES` in `packages/accounts/src/email-send-limit.ts`, read from `SendEmailError.cause.code`). A recipient rejection, such as a suppressed address, or an error with no code keeps the attempt. A database failure on an address's first count is a 500, never a 429.
- A job link is kept only when it is an absolute `http(s)` URL that resolves to the same address on its own and against one of our pages, whose host is a DNS name (only `a-z`, `0-9`, `.` and `-` after the URL parser lowercases it and applies punycode), never an IPv4 or bracketed IPv6 literal, and is not ours: not `rowlandekemezie.com` or a subdomain, the site's own `<subdomain>.workers.dev` or a subdomain, or `localhost`. The build bakes that subdomain in from `WORKERS_SUBDOMAIN` (the `__WORKERS_SUBDOMAIN__` define in `apps/web/vite.config.ts` and the `JobsBackend` build), and falls back to `OWNER_WORKERS_SUBDOMAIN` (`rowland-ekemezie`) when it is unset. `offSiteHref` in `packages/core/src/site.ts` returns the parsed `href` for such a link. Ingest stores that `href`, never the raw input. A role whose link fails the check stays off the board, but ingest still records it as seen in `job_history`, so a link that fails for a day reads as neither a close nor a repost. Each feed logs a `feed` and `unlinked` count for those roles. The log is the only record of them. Every view that links a job or a shortlist mark renders `offSiteHref(url)` as the `href` and renders none when it is empty, so stored rows and old marks are checked again. Link any new job URL the same way. Spellings such as `https:/api/...` parse as host `api` on their own but resolve to our origin on our pages, which is why the check compares both.
- The verify endpoint accepts only `Sec-Fetch-Site: same-origin`, which is what the `/account/confirm` form sends. Browsers that send no fetch metadata (Safari before 16.4, Firefox before 90) cannot finish a magic-link sign-in.
- The edge Worker classifies every path with `edgeRouteOf` before anything else runs. `backend` paths go to `JobsBackend`. `private` paths (`/account/*`) get the static shell and are never server-rendered. Only `public` paths may be rendered or cached. Any `private` response, and any response that sets a cookie, leaves with `cache-control: private, no-store`. `apps/web/test/edge-routing.test.ts` fails if a merge drops one of these rules.
- `/mcp` is an `agent` path. The edge counts each call against `MCP_ANONYMOUS_LIMIT` (no `Authorization` header) or `MCP_TOKEN_LIMIT`, keyed by host and `cf-connecting-ip`, and answers 429 with `retry-after` past the limit. `JobsBackend` ignores session cookies there: no `Authorization` header is an anonymous viewer, a token that names no holder is a 401, a holder who is no longer Pro is a 403, and a Pro holder is a `Member`. Browser requests that carry an `Origin` header are refused, so a page cannot drive a member's tools.
- The MCP server speaks only the stateless protocol (2026-07-28), so it keeps no sessions: Workers isolates share nothing, and stateful sessions leaked memory and broke across isolates. Do not add a stateful protocol version back without a home for sessions. The server is built once per isolate (`HttpRouter.toHttpEffect` in the Worker's init), and each request provides its own `CurrentViewer` from its own `Authorization` header. `toToolkit` merges a request's services over the ones its layer was built with, so never provide `CurrentViewer` to the `McpServer.toolkit` registration layer itself: registration services override the request's.
- Agents get `freeAgentCapabilities` (`listJobs`, `boardStats`, `getJob`) and `proAgentCapabilities` (saved searches and the tracker). Token management (`agentTokens`, `issueAgentToken`, `revokeAgentToken`) is served over `/rpc` only, so a token can never mint a token. The MCP surface sets `ServedSources` to `agentSources()`, which drops every source whose `SourceTerms.agentAccess` is `Forbidden` (Remotive, Himalayas, Hacker News today).
- An agent token is stored as the SHA-256 of its secret in `agent_tokens`; the secret is shown once. Revoking deletes the row.
- Company intel (`packages/core/src/company-intel.ts`) is Pro only. A company page is rendered with no viewer and cached at the edge, so it carries only the free summary, and its listing schema (`JobDetail`) leaves each role's days open and reposts out of the HTML. The browser asks the `companyIntel` capability for the detail once a Pro membership loads. A company's Pro history in `intel_history` is keyed by its exact `companySlugOf` value and role fingerprint. Queries filter indexed `jobs.company_slug` before role deduplication. Rows from a source whose terms forbid paid features are left out; `sourceOfFeedKey` reads the source from the feed key prefix, and `packages/job-sources/test/feed-spec.test.ts` fails if a feed key stops naming its source. The trend counts only weeks since history tracking began, so a fresh stage shows text instead of a chart for four weeks.

## Web feature blueprint

`apps/web/src/features/<name>/` holds a thin route and view. It reads the Model and sends Messages; components never handle transport, retries, or process startup. `apps/web/src/client/<name>/` owns the Foldkit program: Model, Messages, `update`, and named `Command.define` definitions. Remote state lives in the Model, as Foldkit `AsyncData` or a `foldkit/experimental` `Query`. The capability in `packages/core` is the shared typed edge, imported by both sides. A cartridge owns durable behavior.

One send follows one path: feature → Message → `update` → named Command → `RpcClient` over the contract's `toRpcGroup` → shared capability → server-side Durable Object or database cartridge. The server stays authoritative. The Command returns a result Message, and `update` folds it into the Model.
